ASSESSMENT EXAMPLE
CHECKOUT / 45 MIN

THE SCENARIO

Fix duplicate checkout submissions.

A slow response lets a shopper submit the same checkout twice. The result: two orders when they intended one.

FOCUSReliability & verification

01 / TASK BRIEF

Make checkout safe to retry.

Prevent repeated submissions from creating duplicate orders, while allowing a shopper to try again safely if a request fails.

What to deliver
  • A change that prevents duplicate order creation.
  • A safe path for legitimate retries after a failed request.
  • Regression coverage and a brief handoff explaining your decisions.
Working notesYou have 45 minutes. Use the AI and development tools you normally work with. Explain assumptions and anything left out of scope.

02 / CANDIDATE SUBMISSION

A possible handoff.

“I disabled the checkout button while the request is in progress so shoppers get immediate feedback. That alone isn't enough: a refresh or another request can still reach the server.”

“The server recognizes repeated requests using the same checkout key and returns the existing result instead of creating another order. If an attempt fails before an order is created, the same key can be retried safely.”

VerificationTests send duplicate requests and confirm there is one order. A separate test simulates a failed attempt, then confirms a legitimate retry can succeed.

Illustrative handoff, not a real candidate submission.

03 / REVIEWER RUBRIC

Look for the evidence.

CorrectnessRepeated submissions cannot create multiple orders; legitimate retries still work.
VerificationRegression tests exercise duplicate requests and retry behavior.
Engineering judgmentThe handoff explains where the guarantee is enforced and what was left out of scope.
EfficiencyIllustrative elapsed time: 38 of 45 minutes. Token usage: unavailable in this workflow.

The rubric and elapsed time are examples, not a score.

THE POINT Review the result, the verification, and the thinking behind both.

COMMON QUESTIONS

A few things
worth asking.

Can candidates use their own AI tools?

Yes. The concept invites candidates to use AI and the other tools they normally work with. The review focuses on the result and how they verified it.

What kinds of tasks can a team assign?

Tasks could include diagnosing a bug, fixing an integration, shipping a small feature, or improving an existing implementation. Each should have clear constraints and a concrete deliverable.

How would teams compare candidates fairly?

Give candidates the same task, constraints, and expectations, then review their work against the same task-specific rubric. Discuss evidence and tradeoffs rather than relying on a single score.

How do time and token usage factor into the review?

Elapsed time can provide context for a time-boxed task. Token usage is useful only when it is captured and comparable, such as under a defined token budget. Neither replaces evidence that the work is sound.
